## 결정 (이번 주 확정된 것만)

- **작업 선정은 사용자 간트 묶음으로** — v1.1 목록에서 임의로 고르지 않는다. [마감-1]이 첫 적용, "추가 작업 상한" 기준은 이것으로 대체
- **컬럼 불변은 RLS가 아니라 트리거** — `WITH CHECK`는 OLD를 못 보므로 "값이 바뀌었는가"를 정책으로 못 막는다. `BEFORE UPDATE OF <컬럼>` + `WHEN (OLD IS DISTINCT FROM NEW)` + 막기만 하는 공용 함수. 020(#125)의 `WITH CHECK`는 "새 값이 무엇인가"만 막는 것이었고, #43의 "qa↔promo 전환 허용"은 이 차이에서 온 것 (#177)
- **다형성 참조의 뒤처리는 트리거로, 앱 코드 수동 정리는 중복** — `target_id`에 FK가 없어 CASCADE 불가. 사용자 세션으로 도는 수동 정리는 RLS 때문에 본인 것만 지워 고아를 만든다(07/23 1건이 그 증거). 남은 수동 정리는 #176에서 제거 (#148)
- **삭제 UI보다 정리 트리거가 먼저** — 021을 #179보다 앞에 둔 순서. E2E teardown도 같은 이유로 글만 지우면 되게 바뀜
- **수정 요청은 `title`·`content`만 실어 보낸다** — 글 종류·소속 변경은 UI에서 아예 불가능하게 두고 DB 트리거가 이중으로 막음 (#179)
- **RLS에 막힌 쓰기는 에러가 아니라 0행** — 수정·삭제는 `.select("id")`로 반영 행 수를 확인해야 "성공처럼 보이는 실패"를 잡는다 (#179)
- **새 E2E는 옛 코드에서 실패하는지까지 확인한다** — 통과만 보면 "아무것도 안 보는 테스트"를 구분 못 함. #173·#179·#181 전부 적용
- **빈 상태 문구는 예외 없이 유지** — "문구 및 UI 제거" 요청이 와도 문구는 남기고 중복 CTA만 뺀다. 규칙과 부딪히면 규칙이 기본값, 해석이 갈리면 한 줄로 짚고 진행 (#183)
- **린트 보고는 `npm run lint` 전체 기준** — 변경 파일만 검사해 "0"으로 보고했다가 지적받음. #181에서 전체 0으로 만들어 기준선 확보
- **갤러리 글 종류는 "보고 있는 탭"이 정한다** — 토글은 탭과 무관하게 떠서 공지가 엉뚱한 탭에 만들어졌음. 작성 직후 그 탭에 보이게 하면 "사라진 글" 혼란이 구조적으로 없어짐 (#172)
